# Backward Compatibility

The contract surfaces this project protects, and how changes to them must be handled. Review skills check changes against this file, and implementation skills warn when a change breaks it.

> **Current state (2026-10-18, see the dated entries below):** foundation, admin sign-in, storefront browsing and search, the shop-front home page, admin catalog management (categories and products) and the cart. There are a few API routes (listed below), public storefront URLs, internal workspace packages (not published) and the catalog and admin auth schema. There are no external consumers yet. Update this file whenever a new surface appears.

## Protected surfaces

### 1. Public URLs (App Router routes)

- **Where:** `packages/app/src/app/**/page.tsx`. Current storefront URLs (added 2026-10-15, storefront catalog spec Phase 1):
  - `/` (home), with the optional query parameter `category` (added 2026-10-15, Phase 1b: a category slug selecting the featured-products tab; same slug rules as on `/products`; unknown or malformed values silently show all featured products);
  - `/products`, with the optional query parameters `category` (a category slug; unknown or malformed values show "This category does not exist") and `q` (added 2026-10-16, storefront catalog spec Phase 2: a search term, 1 to 100 characters after trimming, matched case-insensitively against names and descriptions and combined with `category` as AND; blank means no search; a longer value shows a validation message; a repeated parameter uses its first value). The header search box and the listing's search form submit these names with `GET`;
  - `/products/<slug>` (`<slug>` is the product slug; drafts and unknown slugs show "Product not found").
  - `/cart` (added 2026-10-16, cart spec Phase 1): the shopper's cart.
  - `/checkout`, `/checkout/pay/<reference>`, `/orders/<reference>` (optional `paid=1`, a fixed code for the "thank you" heading), `/orders/lookup` (added 2026-10-16, cart spec Phases 2–3). `<reference>` is the public order reference `CO-XXXXX-XXXXX-XXXXX-XXXXX` (Crockford base32). Shared links and bookmarks to these URLs must keep working: a new reference format must keep accepting the old one.
  - Since 2026-10-24 (customer accounts, E07 Phase 2): an order placed with a customer account opens on `/orders/<reference>` and `/checkout/pay/<reference>` (and through `confirmDemoPayment`) **only with that customer's session**; without it the answer is the same "not found" as an unknown reference (spec A2). Guest orders keep the bearer-reference rule. No existing link changes: every order placed before E07 Phase 2b is a guest order.
  - Customer account URLs (added 2026-10-24, E07): `/account/sign-in`, `/account/sign-up` (optional `from=checkout`, a fixed code that returns to `/checkout`; optional `error`, a fixed code), `/account` (redirects to `/account/orders`), `/account/orders`, `/account/orders/<id>` (`<id>` is the order uuid, never the public reference; a malformed, unknown or foreign id shows the same "Order not found"). Without a customer session the account pages redirect to `/account/sign-in`.
- **Cart cookie** (added 2026-10-16, cart spec A2): `commerceos_cart`, `HttpOnly`, `SameSite=Lax`, `Path=/`, 30 days, `Secure` when `APP_URL` is https. Value: base64url JSON `{ v: 1, lines: [{ p: <product uuid>, q: <1–99> }] }` (at most 20 lines, no prices). A cart a shopper already holds must keep working: a new format bumps `v`, and an unknown `v` (or anything malformed) reads as an empty cart, never as an error.
- Protected admin URLs (sign-in required; added 2026-10-15, admin catalog spec Phase 1a): `/admin/categories` (optional `notice=deleted`), `/admin/categories/new`, `/admin/categories/<id>` (`<id>` is the category uuid; optional `notice=created`; a malformed or unknown id shows the admin "Not found" page). The `notice` values are fixed codes; anything else is ignored.
- Protected admin URLs (added 2026-10-16, admin catalog spec Phase 1b): `/admin/products`, `/admin/products/new`, `/admin/products/<id>` (`<id>` is the product uuid; optional `notice=created`; a malformed or unknown id shows the admin "Not found" page). The `notice` values are fixed codes; anything else is ignored.
- Protected admin URLs (added 2026-10-17, orders spec Phase 1): `/admin/orders` (optional `page`, a whole number from 1; anything else shows page 1), `/admin/orders/<id>` (`<id>` is the order uuid, never the public reference; a malformed or unknown id shows the admin "Not found" page).
- Protected admin URL (added 2026-10-17, orders spec Phase 3): `/admin` (the dashboard) with the optional query parameter `period` (`7d` or `30d`; missing or any other value shows the last 7 days, never an error). The metric definitions it prints are a product rule (R05): changing one is a coordinated change of `METRIC_DEFINITIONS`, the SQL, the README and the Copilot eval cases. Since 2026-10-19 (date-range spec) it also takes the optional `from` and `to` (`YYYY-MM-DD`, store time zone, both days included; both required, `from ≤ to ≤ today`, at most 366 days, not before 2000-01-01). A valid pair wins over `period`. An invalid pair shows the `period` preset (default 7 days) with an alert, never an error page.
- Protected admin URL (added 2026-10-17, Copilot spec Phase 1): `/admin/copilot` (Commerce Copilot). Optional query parameter `page` (added 2026-10-18, Phase 4: the page of "Your recommendations", a whole number from 1; anything else shows page 1, never an error).
- Protected admin URL (added 2026-10-23, CSV import spec): `/admin/products/import` (CSV product import). No query parameters.
- Admin server actions (`createCategory`, `updateCategory`, `deleteCategory` in `packages/app/src/server/catalog/category.action.ts`; `createProduct`, `updateProduct`, `setProductStatus` in `packages/app/src/server/catalog/product.action.ts`; `changeOrderStatus` in `packages/app/src/server/orders/order-status.action.ts`, added 2026-10-17; `changeRecommendationStatus` in `packages/app/src/server/copilot/recommendation.action.ts`, added 2026-10-18; `submitProductImport` in `packages/app/src/server/catalog/product-import.action.ts`, added 2026-10-23) are POST endpoints used only by this app's forms. So are the public shopper actions `addToCart`, `updateCartLine`, `removeCartLine`, `acceptCartChanges` (`packages/app/src/server/cart/cart.action.ts`) and `placeOrder`, `confirmDemoPayment`, `lookupOrder` (`packages/app/src/server/orders/order.action.ts`), added 2026-10-16, which need no session; the cart actions change only the caller's cart cookie. Their `FormData` field names and the `ActionState` shape are internal and may change with the forms.
- **Breaking:** removing or renaming a public route, or changing the meaning of its query parameters.
- **Required path:** add a redirect in `next.config.ts` (`redirects()`) and note the change in the PR description.

### 2. HTTP API (Route Handlers)

- **Where:** `packages/app/src/app/**/route.ts`. Current endpoints:
  - `GET /api/health` (response: `{ status: "ok" | "degraded", components: [{ name, status, latencyMs }] }`, 200/503).
  - `GET /api/admin/me` (`ApiResult<{ id, email, role }>`, 200/401).
  - `POST /api/admin/copilot/answers` (added 2026-10-17, Copilot spec Phase 1): body `{ question: string (1–500 after trimming) }` or `{ intent: "focus" | "top_products" | "low_stock" | "sales_change" | "traffic_sources" | "funnel" | "views_without_sales" }`, exactly one. Response `ApiResult<CopilotAnswerDto>` (`packages/ai/src/copilot/copilot-answer.ts`: `answerId` (since 2026-10-18, Phase 4: the stored answer's id; `null` for declined and unsupported questions and for an answer without recommendations), `kind`, `intent`, `question`, `origin`, `fallbackReason`, `model`, `period`, `summary`, `summaryEvidence[]` (added 2026-10-17, Copilot spec Phase 3: the facts the summary cites, as evidence rows), `missingData?`, `recommendations[]` (each `id` is the stored recommendation's id since Phase 4; `status` is `new`), `limitations[]`, `definitions[]`). Statuses 200/400/401/429 (error code `RATE_LIMITED`, 10 questions per owner per 10 minutes)/500. An AI provider failure is never an HTTP error: it is a 200 with `origin: "rules"` and a `fallbackReason`.
  - `POST /api/admin/products/description-drafts` (added 2026-10-19, descriptions spec Phase 1): body `{ name: string (1–200 after trimming), categoryId?: string (uuid or ""), price?: string ("" or a form price such as 249.90 / 249,90), notes?: string (at most 5000 after trimming) }`. Response `ApiResult<DescriptionDraftDto>` (`packages/ai/src/descriptions/description-draft.dto.ts`): `{ kind: "draft", text, model, promptVersion, fieldsUsed: ("name" | "category" | "price" | "notes")[], demoMarked }` or `{ kind: "unavailable", reason: "not_configured" | "insufficient_input" | "timeout" | "rate_limited" | "provider_error" | "auth" | "refused" | "daily_limit" | "invalid_output" }`. Statuses 200 (both kinds)/400 (invalid body or unknown category, field errors)/401/429 (`RATE_LIMITED`, 5 drafts per owner per 10 minutes)/500. Nothing is stored; no request field is echoed back.
  - `/api/auth/*`: Better Auth's own endpoints (`POST /sign-in/email`, `POST /sign-out`, `GET /get-session`). Their shapes belong to the library pinned at `~1.7.10`; upgrades are reviewed against the admin e2e suite.
  - `/api/customer-auth/*` (added 2026-10-24, E07 Phase 1): the customer Better Auth instance. Only `POST /sign-up/email`, `POST /sign-in/email`, `POST /sign-out` and `GET /get-session` answer; any other method or path is 404 (route allowlist plus `disabledPaths`). Shapes belong to the library pinned at `~1.7.10`.
  - `GET /api/account/orders` (added 2026-10-24, E07 Phase 2b): `ApiResult<{ orders: { id, reference, createdAt, status, total: { amountMinor, currency } }[]; capped: boolean }>` (the newest 50, newest first), 200/401 (401 without a customer session, an owner session included).
  - `GET /api/account/orders/<id>` (added 2026-10-24, E07 Phase 2b): `ApiResult<CustomerOrderDto>` (the summary plus `items`, `subtotal`, `shipping`, `paidAt`, `paymentProvider`, `contact`, `shippingAddress`), 200/401/404. A malformed, unknown or foreign id is the **same** 404 body; there is no 400 on this route.
- **Breaking:** removing an endpoint or method; removing or renaming a response field; changing a field's type; adding a new required request field; changing status codes or the error format.
- **Required path:** make additive changes only, or ship a new versioned endpoint. Mark the old one deprecated and keep it for at least one release, and write a migration note in the PR.

### 3. Monorepo packages (`packages/*`)

- **Where:** what each package exports from its entry point (`package.json` `exports` / `main`).
- **Breaking:** removing or renaming an export, or changing a function signature or type in an incompatible way.
- **Required path:** deprecate first (`@deprecated` JSDoc), update every consumer in the monorepo in the same PR, and bump the major version if the package is published.

### 4. Configuration and environment variables

- **Where:** `packages/app/next.config.ts`, env variables validated in `packages/app/src/server/env.ts` (documented in `.env.example`), `.ai/agentic.config.json`.
- **Added 2026-10-15:**
  - `BETTER_AUTH_SECRET` (required);
  - `AUTH_TRUSTED_IP_HEADER` (optional);
  - `ADMIN_EMAIL` / `ADMIN_PASSWORD` (read only by `npm run admin:create`);
  - `APP_URL` became required when `NODE_ENV=production`.
- **Added 2026-10-17 (Commerce Copilot, Phase 2):** `LLM_PROVIDER` (optional; `gemini` is the only accepted value), `LLM_API_KEY` and `LLM_MODEL` (both required when `LLM_PROVIDER` is set). An empty string counts as unset; without a provider the Copilot answers with rule-based insights.
- **Added 2026-10-23 (agent workshop hardening):** the validation gate in `.ai/agentic.config.json` gained `npm run test:hooks` (additive; also a step of the CI `lint` job, whose check name is unchanged). The committed agent settings `.claude/settings.json` (deny rules and the PreToolUse hook) apply to every Claude Code session in this repository; loosening them is a change the user approves.
- **Added 2026-10-24 (customer accounts, E07 Phase 1):** `CUSTOMER_AUTH_SECRET` signs the customer Better Auth instance. Optional in development and test (falls back to `BETTER_AUTH_SECRET`); **required in production and different from `BETTER_AUTH_SECRET`**, so a production start without it fails at startup by design (the `APP_URL` precedent). Any CI step or deployment that starts the production build must set it.
- **Breaking:** renaming or removing an environment variable, or changing a config key's format.
- **Required path:** support the old name as a fallback for one release and document the change in the PR and README.

### 5. Data schema (PostgreSQL via MikroORM migrations)

- **Where:** `packages/database/src/migrations/`, `packages/database/src/entities/`.
- **Breaking:** dropping or renaming a column or table, narrowing a type, adding a NOT NULL column without a default, or editing an already-applied migration.
- **Required path:** migrations only move forward and committed migrations are never edited. Destructive changes are rolled out in steps (add the new column → backfill → switch code → drop the old one in a later migration).
- `stock_adjustments` (added 2026-10-16, admin catalog spec Phase 2): the manual stock history (`product_id`, `previous_quantity`, `new_quantity`, `created_at`; checks `>= 0` and `new_quantity <> previous_quantity`; `on delete cascade` from `products`). A later `reason` or `source` column (for example checkout decrements) is added with a default, never as a required column.
- `orders`, `order_items` (added 2026-10-16, cart spec Phase 2, `Migration20261016132205_orders`): orders with snapshots, integer money, the full status workflow (`pending_payment`, `paid`, `processing`, `shipped`, `cancelled`, `refunded`) and paid-at checks; unique `public_reference`, `idempotency_key`, `payment_reference`; `order_items.product_id` `on delete set null`, `order_id` `on delete cascade`. Orders hold personal data (name, email, address).
- `rate_limit_buckets` (added 2026-10-16, cart spec Phase 3, `Migration20261016132222_rate_limit_buckets`): fixed-window counters keyed by `(key, window_start)`.
- `traffic_daily_stats`, `product_view_daily_stats` (added 2026-10-17, orders spec Phase 2, `Migration20261017130131_demo_traffic`): **seeded, fictional** demo traffic (D08), regenerated by every `npm run db:seed`. `traffic_daily_stats`: unique `(date, source)`, `source` in `direct`, `organic`, `social`, `email`, `paid`, counts `>= 0` and the funnel check `sessions >= product_views >= add_to_carts >= checkouts_started`. `product_view_daily_stats`: unique `(date, product_id)`, `on delete cascade` from `products`, `views >= add_to_carts >= 0`. Rollback: `down` drops both tables and nothing else. Their only reader is the Copilot's `getTrafficSummary` (E05-S04, `DatabaseTrafficStats`, read-only), which labels the data as fictional.
- `copilot_recommendations` (added 2026-10-18, Copilot spec Phase 4, `Migration20261018180016_copilot_recommendations`): every recommendation Copilot showed (`answer_id` groups one answer), with `intent`, `origin` (`llm`, `rules`), `fallback_reason`, `provider`/`model`/`prompt_version` (LLM answers only), the period, the text, `evidence` (jsonb array of `{ metric, value, period?, source, demo? }`), `limitations` and `related_product_ids` (jsonb arrays; product ids **without** a foreign key), and the owner's `status` (`new`, `saved`, `dismissed`, `completed`) with `status_changed_at` (null exactly while `new`). Checks for every enum and invariant; indexes on `answer_id` and `(status, created_at)`. No personal data and no question text. Rollback: `down` drops only this table; nothing else references it. A new status or origin is added by widening its check in a new migration.
- `customer_users`, `customer_sessions`, `customer_accounts`, `customer_verifications`, `customer_rate_limits` (added 2026-10-24, E07 Phase 1, `Migration20261024181620_customer_auth`): the customer Better Auth instance's tables, mirroring Better Auth 1.7.10's generated schema, plus `check (role in ('customer'))`. Rollback: `down` drops only these tables and fails while any foreign key points at `customer_users` (no `cascade`).
- `orders.customer_id` (added 2026-10-24, E07 Phase 2a, `Migration20261024193652_orders_customer`): nullable, foreign key to `customer_users` `on delete restrict` (an account row can never be deleted from under its orders), index `(customer_id, created_at)`; no backfill, so earlier orders are guest orders and are never attached later (spec A3). Set once at placement from the session, never changed. Rollback (owner decision D-d): `down` locks `orders` and **refuses while any order has a `customer_id`** (dropping it would reopen account orders by reference), so once account orders exist, fixes go forward only; `orders_customer` must be rolled back before `customer_auth`.
- Demo orders (`public_reference` `DEMO-NNNN`) are seed data: the seed deletes and regenerates them. A real order must never use the `DEMO-` prefix (checkout generates `CO-` only; a unit test pins it).

## General rules

- Prefer additive changes over modifying or removing existing ones.
- Any intentional break needs the `risk-high` label, a migration note in the PR description, and the user's approval.
