## 2. Environment variables

Names only. Values are secrets or deployment-specific and never go in this file or in the repository. The list is the one in `packages/app/src/server/env.ts` at the tag, which matches `main`. It is also in `.env.example`.

Required:

- `DATABASE_URL`: a `postgres://` or `postgresql://` connection string.
- `BETTER_AUTH_SECRET`: at least 32 characters. Signs the admin sign-in.
- `APP_URL`: the public origin, for example `https://<your-domain>`. Required when `NODE_ENV=production`; the app does not fall back to localhost in production.
- `CUSTOMER_AUTH_SECRET`: at least 32 characters. Required when `NODE_ENV=production`. It must differ from `BETTER_AUTH_SECRET`; a production start fails otherwise.

Optional:

- `NODE_ENV`: `development`, `test` or `production`. Defaults to `development`.
- `DATABASE_DEBUG`: `true` or `false`. Logs SQL. Defaults to `false`.
- `AUTH_TRUSTED_IP_HEADER`: a lowercase header name, for example `x-real-ip`. Set it only behind a proxy that overwrites that header. Unset, sign-in is rate-limited globally.
- `LLM_PROVIDER`: `gemini`, or unset. When unset, Commerce Copilot gives rule-based answers and makes no network call.
- `LLM_API_KEY` and `LLM_MODEL`: both required when `LLM_PROVIDER` is set. An empty string counts as unset.

Used by a command, not by the running app:

- `ADMIN_EMAIL` and `ADMIN_PASSWORD`: read only by `npm run admin:create`, which creates the owner account. The password needs at least 12 characters.

Operator notes:

- `packages/app/next.config.ts` loads the repository-root `.env` file if one exists, for variables that are not already set. Do not ship a `.env` file in a deployed image; set the variables in the platform.
- Set the variables before the first start. The environment is validated when it is first read, and a missing or invalid required variable fails with a message that names it.

17. `Migration20261027100100_demo_category_images`

Points to know before running them:

- A fresh database runs all 17. An existing 0.x database (none is known to exist) would run the same list.
- Migrations 11, 13, 14, 15 and 17 also change data (7 creates tables; 12 and 16 add columns). They update only rows that match demo slugs, SKUs or `DEMO-` references (see their `WHERE` clauses). Check that no real product or order on the target database uses those values.
- The CLI has `up` and `create` only. There is no command to run a `down` migration; see the procedure's rollback section.
- The migration runner is started with `tsx` (`packages/database`, script `migrate`). Whether `tsx` is in the runtime image is a platform decision. To fill in when the platform is chosen.
- `npm run db:seed` regenerates demo data (demo orders with the `DEMO-` prefix and the demo traffic tables). Run it only on a demo store, never on a store with real orders.

## 4. Known limitations (from the changelog)

- Payments, shipping and taxes are simulated. The demo store takes no money.
- No public deployment existed at the tag.
- Owner review on 320, 768, 1024 and 1440 px in light and dark is pending for the admin and Copilot screens.
- On 320 px, seven primitive Storybook documentation pages scroll sideways by about 30 px.

## 5. Version question (owner decision)

The version numbers disagree:

- The git tag and the changelog say `1.0.0` (tag `v1.0.0` on commit `86a5090`).
- `package.json` in the root and in all five `packages/*` says `0.1.0`. All of them are `"private": true`, so nothing is published to npm from them.
- There is no GitHub Release for `v1.0.0`.

This PR does not change `package.json`. The owner must choose one rule:

- **A (recommended for now):** keep the `0.1.0` package versions, and treat the git tag and `CHANGELOG.md` as the release version. Write this rule in [procedure.md](procedure.md). The tag is already published and must not move.
- **B:** bump every `package.json` to `1.0.0` in a commit on `main` and move the tag to that commit. This rewrites a published tag, so it needs the owner's explicit approval.
- **C:** bump every `package.json` at the next release (for example to `1.0.1`) and record that rule. The tag `v1.0.0` keeps the old `package.json` values.

Lesson 22 says not to bump `package.json` from the release skill; lesson 24 says to bump all of them. The repository needs one rule, and the owner picks it.

Also decide whether to create the GitHub Release `v1.0.0` now (`gh release create v1.0.0 --verify-tag --notes-file docs/releases/1.0.0.md`). That is a write to the remote, so it needs the owner's go.
